1. 설명
● 목표 : 시간에 따른 트렌드 변화를 분석하여, 이해 및 정보 제공

2. 기술스택
● Python (instaloader, tkinter, threading, PIL, requests)
3. 설계
● 구조 설계 : 데이터 수집 / 점수 산출 / UI 3개 모듈로 분리하고 모듈 간 데이터 형식을 사전 합의해, 팀원 3인이 상호 대기 없이 병렬 개발 가능한 체계 구축

● 문제점 2 : 다수 계정 스크래핑 중 UI가 응답하지 않고, 비공개 계정·네트워크 오류 발생 시 프로그램 전체가 중단
● 해결 방안 2 : 수집 로직을 별도 스레드로 분리해 UI 응답성 확보. 수집·점수 계산 전 구간에 예외 처리와 logging을 적용해 개별 계정 실패가 전체 실행에 영향을 주지 않도록 구조 개선
● 프로젝트 완수 : 최종 결과보고서 및 발표에서 설계 목표 달성도 90% 달성
● 역량 향상 : 정량 지표 기반 평가 알고리즘 설계 능력 및 예외 상황을 고려한 안정적 프로그램 구조 설계 능력 향상

구분
팀 프로젝트
프로젝트 명
주차 관리 시스템
활동 및 역할
C#·MySQL을 활용해 차량 입출차와 요금을 관리하는 데스크톱 프로그램 개발 - 팀원 (5인) / DB 연동 및 설정 기능, UI 구성·데이터 시각화 담당
주요내용
1. 설명
● 목표 : 실제 주차장에서 사용 가능한 수준의 차량 입출차·요금 관리 프로그램 구현
● 중점 : 데이터베이스 연동을 통한 기록 영속화, 주차 현황의 직관적 시각화
2. 기술스택
● C# WinForms, MySQL
3. 설계
● 문제점 1 : 프로그램 종료 시 입출차 기록이 모두 소실되어 실사용 불가. 또한 DB 접속 정보가 코드에 고정되어 있어 환경이 바뀔 때마다 소스 수정이 필요
● 해결 방안 1 : MySQL 연동으로 입차·출차·요금 데이터를 영구 저장하고 재실행 시 자동 복원되도록 구현. 별도 설정 폼(Setting)을 제작해 서버 주소·계정·최대 주차 면수를 프로그램 내에서 입력하고, 연결 테스트와 DB·테이블 자동 초기화까지 수행하도록 개선하여 소스 수정 없이 어떤 환경에서도 구동 가능하도록 함
● 문제점 2 : 설정 폼에서 변경한 값이 메인 폼에 즉시 반영되지 않고, 텍스트로만 표시된 주차 현황은 혼잡도를 파악하기 어려움
● 해결 방안 2 : 정적 공유 클래스(SharedData)를 도입해 폼 간 설정값을 일원화하고, 저장 시 메인 폼의 연결 정보와 최대 수용량이 즉시 갱신되도록 구조화. ProgressBar로 실시간 혼잡도를, Chart로 시간대별 입차 대수를 시각화해 현황을 한눈에 파악할 수 있도록 개선
4. 메인 기능
● 사용성 개선 : 입출차 내역·혼잡도·시간대별 통계를 단일 화면에서 확인할 수 있도록 구성해 관리자의 현황 파악 단계를 단순화
5. 상세기능
● 문제점 3 : 차량 번호 오입력·중복 입차·정원 초과 시 잘못된 데이터가 그대로 저장되는 문제
● 해결 방안 3 : 번호 자릿수 검증, 기존 입차 상태 조회를 통한 중복 등록 차단, 정원 초과 시 입차 거부 로직을 추가하고 모든 처리 결과를 로그로 남겨 원인 추적이 가능하도록 구현
● 실사용 가능성 확보 : 데이터 영속화와 프로그램 내 DB 설정 기능을 통해, 소스 수정 없이 설치 환경에 맞춰 바로 운영 가능한 형태로 완성
● 안정성 강화 : 입력 검증 3단계 및 예외 처리·로그 기록 적용으로 비정상 데이터 저장 차단
● 역량 향상 : 데이터베이스 연동과 폼 간 상태 공유 구조에 대한 이해, 수업에서 다루지 않은 WinForms 기능을 직접 학습해 적용하는 능력 향상

주요내용
1. 설명
● 목표 : 도서 검색부터 독후감 작성·공유, 이용자 간 소통까지 이어지는 커뮤니티형 독서 플랫폼 구현
2. 기술스택
● Java, Spring Boot, MySQL(MariaDB), Redis, WebSocket(STOMP), HTML/CSS, 알라딘 Open API
3. 설계
● 중점 : 계층형 백엔드 구조 설계, 실시간 채팅 구현, 외부 API 연동
● 문제점 1 : 게시글·좋아요·댓글·친구·채팅·스터디 등 기능이 늘어나면서 코드가 서로 얽혀 수정 시 영향 범위를 예측하기 어렵고, 6인 팀에서 동시 작업 시 충돌이 잦음

● 구조 설계 : 7개 테이블과 약 40개 클래스를 계층·도메인 기준으로 정리해 6인 팀이 병행 개발 가능한 구조 확립
4. 메인 기능
● 서비스 완성 : 회원가입·로그인·비밀번호 찾기, 도서 검색, 독후감 CRUD, 공개/비공개 설정, 좋아요·댓글, 친구 요청 및 수락, 실시간 채팅, 스터디 모집, 회원 정보 수정·탈퇴, 관리자 권한 관리까지 커뮤니티 서비스의 핵심 기능을 모두 구현
5. 상세기능
● 문제점 2 : 사용자 간 1:1 채팅에서 단순 요청-응답 방식으로는 실시간 전달이 불가능하고, 새로고침·재접속 시 대화 내용이 사라짐
● 해결 방안 2 : WebSocket과 STOMP로 실시간 양방향 통신을 구성하고, Redis Pub/Sub 구조(Publisher-Subscriber)를 도입해 메시지를 채널 단위로 분배하도록 설계. 동시에 대화 내용을 DB 테이블에 저장해 재접속 후에도 이전 기록을 복원하도록 구현
● 문제점 3 : Redis를 팀원 각자의 PC에 설치·설정해야 해 개발 환경 구축 단계에서 시간이 소요되고 실행 실패가 반복됨
● 해결 방안 3 : 애플리케이션 구동 시 내장형 Redis 서버가 함께 실행되도록 구성해 별도 설치 없이 동작하도록 개선. 아울러 환경별 예외 상황에 대비해 수동 설치·검증 절차를 담은 설치 매뉴얼을 문서화하여 배포

● 역량 향상 : Spring Boot 기반 웹 애플리케이션 설계, 캐시·메시지 브로커 활용, 외부 API 연동 및 보안 처리 경험 축적

구분

아두이노 우노 R4 보드를 이용한 사물인터넷(IoT) 구현
활동 및 역할
TCP/IP 소켓 통신 기반으로 LED 원격 제어 및 온습도 실시간 모니터링 시스템 구축 - 팀원 (4인) / 아두이노 펌웨어, TCP 서버, PC 클라이언트, 안드로이드 앱 구현 담당
주요내용
1. 설명
● 목표 : 원격지에서 아두이노에 연결된 LED 4개를 제어하고 DHT11 센서의 온·습도를 실시간 모니터링하는 IoT 시스템 구현
2. 기술스택
● Arduino(C/C++), C#(.NET 소켓·WinForms), Java(Android), DHT11 센서
3. 설계
● 중점 : 서버-클라이언트 구조 설계, PC·모바일 다중 클라이언트 지원, 실시간 데이터 시각화
● 문제점 1 : 아두이노는 시리얼 통신만 지원해 물리적으로 연결된 PC에서만 제어가 가능하며, 원격 제어라는 목표를 충족할 수 없음
● 해결 방안 1 : 아두이노와 시리얼로 연결된 PC에 C# TCP 서버를 두어 시리얼↔TCP 브리지 역할을 수행하도록 설계. 서버가 네트워크 명령을 시리얼 신호로 변환해 전달하고 센서 값을 반대 방향으로 중계하도록 구현해, 네트워크상의 모든 클라이언트가 제어 가능한 구조로 확장
4. 메인 기능
● 시스템 완성 : 센서-펌웨어-서버-클라이언트로 이어지는 IoT 전 계층을 직접 구현하고, PC와 스마트폰 양쪽에서 동일한 제어·모니터링이 동작하는 것을 실증
5. 상세기능
● 문제점 2 : LED 4개를 개별 명령으로 제어하면 명령 종류가 급증하고, 클라이언트 종류(PC·모바일)마다 통신 규약이 달라져 서버 코드가 중복될 우려

성장 과정

저는 3년간 다섯 개의 팀 프로젝트를 거치며, 코드를 짜는 사람에서 구조를 설계하는 사람으로 옮겨왔습니다.
시작은 2024년 1학기, 소셜 미디어 데이터 분석 프로젝트의 팀장이었습니다. 인스타그램 게시물을 수집해 인기순으로 정렬하는 도구를 만들었는데, 완성하고 보니 상위권이 전부 팔로워가 많은 계정으로 채워져 있었습니다. 정렬 코드에는 오류가 없었습니다. 문제는 "무엇이 좋은 게시물인가"를 좋아요 수 하나로 정의한 저에게 있었습니다. 좋아요·해시태그·팔로워에 서로 다른 가중치를 부여해 지표를 다시 설계하고 나서야 납득할 만한 결과가 나왔습니다. 기능이 동작하는 것과 목적을 달성하는 것은 다른 문제라는 사실을, 첫 프로젝트에서 배웠습니다.
그해 2학기에는 두 가지를 동시에 겪었습니다. C#으로 만든 주차 관리 시스템에서는 프로그램을 끄면 모든 기록이 사라진다는 사실을 마주하고 MySQL을 연동해 데이터를 영속화했고, 접속 정보를 코드에 박아두지 않도록 설정 화면을 따로 만들었습니다. 같은 학기 독서록 공유 웹 사이트에서는 백엔드 전 영역을 맡아 Spring Boot로 약 40개 클래스와 7개 테이블을 설계했습니다. 기능이 늘어날수록 코드가 서로 얽혀 수정 한 번에 영향 범위를 가늠하기 어려워졌고, 계층과 도메인을 기준으로 구조를 나누고 나서야 여섯 명이 동시에 작업할 수 있었습니다.
2025년에는 두 방향으로 시야를 넓혔습니다. 아두이노 기반 IoT 프로젝트에서는 센서·펌웨어·서버·PC·모바일로 이어지는 전 계층을 직접 연결하며, 서로 다른 시스템이 만나는 지점에서 규약을 먼저 정하는 일이 얼마나 중요한지 배웠습니다. 소프트웨어공학 수업의 카페 운영 시스템에서는 UML 설계와 테스팅, 위험 관리까지 개발의 전 주기를 문서로 다뤄봤습니다.
돌아보면 매 프로젝트에서 배운 것은 결국 하나로 모입니다. 처음에는 돌아가는 코드를 만드는 데 급급했지만, 지금은 코드를 쓰기 전에 왜 이 구조여야 하는지를 먼저 설명할 수 있게 되었습니다. 저는 이 변화를 제 성장의 축으로 여기고 있습니다.
성격 장·단점

장점 &#8212; 아는 것을 나눠 팀 전체의 속도를 올립니다
카페 운영 시스템 프로젝트에는 Spring Boot를 처음 접하는 팀원이 있었습니다. 백엔드 인력이 한 명 비는 상황이었지만, 그 팀원의 몫을 제가 대신 처리하는 대신 함께 작업하는 방식을 택했습니다. 프로젝트 구조와 코드 작성 방식을 처음부터 설명하고, 초반에는 같은 화면을 보며 코드를 작성했습니다.
설명하는 과정에서 제 이해도 함께 깊어졌습니다. 남에게 납득시키려면 제가 관성적으로 쓰던 코드의 이유를 스스로 정리해야 했기 때문입니다. 결과적으로 그 팀원은 프로젝트 후반부에 독립적으로 기능을 구현했고, 팀 전체의 개발 속도도 회복됐습니다. 독서록 프로젝트에서 개발 환경 설치 매뉴얼을 따로 작성해 배포한 것도 같은 이유였습니다. 제 진도만 빨라지는 것은 팀의 성과가 아니라고 생각합니다.

단점 &#8212; 구현부터 시작하려는 습관, 그리고 교정 과정
저는 원래 설계 문서보다 코드를 먼저 여는 사람이었습니다. 혼자 하는 과제에서는 그 편이 빨랐기 때문에 오래 굳어진 습관이었습니다. 하지만 카페 운영 시스템에서 이 방식은 명확한 대가를 치렀습니다. 기능이 쌓일수록 쓰이지 않는 더미 코드가 남았고, 초기 설계를 중간에 바꾸면서 코드 전반의 방향성이 흐트러졌습니다. 수정 한 번에 팀원 여러 명과 조율해야 하는 상황이 반복됐습니다.
가치관

문제 해결의 시간은 혼자 고민한 시간이 아니라 함께 본 관점의 수에 반비례합니다.
프로젝트를 거치며 제가 반복해서 선택한 행동이 있습니다. 일을 시작하기 전에 팀이 공유할 기준부터 만드는 일입니다.
첫 프로젝트에서는 수집·알고리즘·UI 세 모듈로 나누기 전에, 게시물 데이터를 어떤 형태로 주고받을지부터 팀원들과 합의했습니다. 그 덕분에 세 명이 서로를 기다리지 않고 병렬로 작업할 수 있었습니다. IoT 프로젝트에서는 응답 형식을 JSON으로 규격화해, PC 클라이언트와 안드로이드 앱이 같은 서버 코드를 그대로 쓰도록 만들었습니다. 카페 운영 시스템에서는 요구사항 변경이 잦아 진행 상황 공유가 어려워지자 Jira를 도입해 작업을 티켓 단위로 관리했습니다.
이런 선택의 바탕에는 경험이 있습니다. 혼자 붙잡고 있을 때는 보이지 않던 오류가, 팀원과 이야기하는 중에 드러나는 일을 여러 번 겪었습니다. 좋아요 정렬의 편향을 발견한 것도, 설계 변경으로 인한 재작업을 줄인 것도 결국 대화를 통해서였습니다. 그래서 저는 좋은 개발자의 조건을 개인의 처리 속도가 아니라 팀이 같은 그림을 보게 만드는 능력이라고 생각합니다. 규약을 먼저 정하고, 알게 된 것을 문서로 남기고, 모르는 사람을 기다려주는 일이 결국 가장 빠른 길이라고 믿습니다.
업무상 강점 및 경력사항

강점 1. Spring Boot 기반 백엔드 설계·구현 경험
두 개의 서비스에서 백엔드를 담당했습니다. 독서록 공유 웹 사이트에서는 백엔드 전 영역을 맡아 Controller-Service-Repository-Entity-DTO 계층 구조로 약 40개 클래스와 7개 테이블을 설계했고, WebSocket과 STOMP에 Redis Pub/Sub을 결합해 실시간 채팅을 구현했습니다. 대화 내용은 DB에 저장해 재접속 후에도 복원되도록 처리했으며, 회원 비밀번호는 AES 암호화를 적용해 저장했습니다. 알라딘 Open API를 연동한 REST 컨트롤러로 도서 정보를 조회하고 이를 테이블에 저장해 게시글과 연결했습니다.
카페 운영 어시스턴트에서는 시스템 설계와 함께 관리자 인증, 회원·직원·메뉴·근태·옵션 API를 개발하고 전체 코드 리팩토링을 수행했습니다. 결제·포인트 적립·재고 차감이 하나의 주문에서 연쇄적으로 일어나는 구조라 데이터 무결성을 최우선 위험으로 식별하고 트랜잭션 단위 처리를 적용했습니다.
강점 2. 데이터의 수집부터 시각화까지 전 구간을 다뤄봤습니다
인스타그램 크롤링으로 데이터를 수집하고, 가중치 기반 점수 체계로 가공한 뒤 순위로 제시하는 파이프라인을 직접 설계했습니다. 주차 관리 시스템에서는 입출차 기록을 MySQL에 적재하고 시간대별 통계를 차트로, 실시간 혼잡도를 진행 바로 시각화했습니다. IoT 프로젝트에서는 센서 값을 시계열 그래프로 렌더링하되 최근 50개 포인트만 유지하도록 처리해 장시간 실행 시 성능이 저하되지 않게 했습니다. 데이터가 어디서 들어와 어떻게 쌓이고 무엇으로 보여야 판단에 쓰이는지를 각 단계에서 경험했습니다.
강점 3. 서로 다른 시스템을 연결하는 통합 역량
IoT 프로젝트에서 아두이노 펌웨어, C# TCP 서버, WinForms 클라이언트, 안드로이드 앱까지 네 개 구성 요소를 연결했습니다. 시리얼 통신만 가능한 아두이노를 서버가 TCP로 중계하도록 브리지 구조를 설계했고, LED 상태를 4비트 이진수 한 개로 표현해 단일 명령으로 16가지 조합을 제어했습니다. 응답을 JSON으로 통일한 덕분에 클라이언트를 추가해도 서버를 수정할 필요가 없었습니다. 언어와 플랫폼이 달라도 인터페이스를 먼저 정하면 연결된다는 것을 실제로 확인했습니다.
강점 4. 설계 문서와 품질 검증 절차에 익숙합니다
소프트웨어공학 프로젝트에서 유스케이스 명세, 클래스·시퀀스 다이어그램, 데이터베이스 설계서를 작성하고 30여 개 유스케이스를 구현했습니다. 블랙박스·화이트박스 테스팅으로 필수값 누락, 중복 등록, DB 저장 실패 같은 예외 흐름을 사전 검증했고, 위험 요소를 발생 확률과 영향도로 등급화해 대처 방안을 수립했습니다. 코드만 아는 것이 아니라 문서로 합의하고 검증하는 절차를 함께 겪었다는 점이 제 강점입니다.
